# ADR 0003: DDSKK が引けるように、辞書の 1 行の長さに上限を設ける

ステータス: 採択（未実装）

## 文脈

[ADR 0002](0002-bang-prefixed-headwords.md) の実装の後に DDSKK で確かめたところ、EUC-JP 版の見出し語の一部を DDSKK で引けないと分かった。
`!` を付けない見出し語でも起き、[ADR 0002](0002-bang-prefixed-headwords.md) より前の v0.1.5 から続いている不具合である。

### DDSKK の二分探索

DDSKK の辞書の検索（`skk.el` の `skk-search-jisyo`）は、範囲の幅が `limit` を超えている間、二分探索で範囲を狭める。
範囲の中央の位置から行頭に戻った位置が範囲の先頭（`min`）と同じになると、範囲の終わり（`max`）を `min` にして二分探索を終える。
その後の `search-forward` は `max` までしか探さないので、目的の見出し語は見つからない。

この状態は、範囲の幅が `limit` を超えているのに、範囲の先頭の行が幅の半分より長いときに起きる。
DDSKK は主辞書と `skk-extra-jisyo-file-list` の辞書を `limit` 10000 で引くので、5,000 文字以上の行があると、その行の後ろの見出し語を見落とすことがある。
行の長さは、DDSKK のバッファでの文字数（EUC-JP 版を読んだ後の文字数）である。

### 引けない見出し語の数

2026-10-22 に、DDSKK（`ddskk-17.2_Mena`、Emacs 30.1、日本語の言語環境）で、EUC-JP 版のすべての見出し語を `skk-search-jisyo-file` と `limit` 10000 で引いた。

| 辞書 | 見出し語 | 最長の行 | 引けない見出し語 |
|---|---|---|---|
| v0.1.5 | 8,655 | 57,813 文字 | 1,159 |
| main（コミット 2b7a9fb） | 17,310（`!` の付いたもの 8,655） | 57,814 文字 | 2,317（`!` の付いたもの 1,094） |

- 見出し語は `skk-string<` の昇順に並んでおり、並び順の誤りではない。線形探索（`limit` 0）では引ける
- 引けない例: `はーと`、`abacus`、`らんどせる`。`はーと` 自体の行が長いだけでなく、長い行の後ろにある短い行（`abacus` など）も引けない
- AquaSKK（codefirst/aquaskk のコミット 0e7a88f のエンジン）では、`はーと`、`!はーと` も引ける
- この数は、数値変換（`skk-use-numeric-conversion`）を切って数えた。数値変換が有効なまま `skk-search-jisyo-file` を呼ぶと、数字を含む見出し語（`whale2`、`12じ` など。`!` の付いたものを含め 216 個）も引けないように見える。
  実際のキー入力（`/ w h a l e 2 SPC`、`/ 1 0 0 SPC`）では、DDSKK は数字を含む見出し語も引くので、これは検査の方法による見かけの失敗である。
  [ADR 0002](0002-bang-prefixed-headwords.md) の実装で `docs/specifications.md` と README に書いた数（1,242、2,483）は、この見かけの失敗を含んでいた

### 長い行の原因

5,000 文字以上の行は 53 個（`!` を付けない見出し語の数。`!` の付いた行も同じ数ある）で、広い意味の読みに多くの絵文字が集まった行である。

| 見出し語 | 候補 | 行の長さ（EUC-JP 版） | 主な原因 |
|---|---|---|---|
| `じょせい` | 785 | 57,813 | Mozc の読み（107 個の絵文字とその肌の色違い 670 個） |
| `かっぷる` | 312 | 30,838 | 2 人の肌の色の組み合わせ（12 個の絵文字の肌の色違い 300 個） |
| `はーと` | 251 | 23,399 | Mozc の読みの肌の色違い（200 個） |
| `かお` | 390 | 15,614 | Mozc の読み（200 個の絵文字と肌の色違い 190 個） |
| `はた` | 269 | 11,155 | Mozc の読み（264 個の国旗） |

EUC-JP 版の候補は `(concat "\U0001F469\U0001F3FB‍...")` のような Lisp の式なので、1 つの候補が 30〜100 文字になる。

### 直し方の比較

| 案 | 5,000 文字以上の行 | 引けなくなる絵文字 |
|---|---|---|
| A: Mozc の読みの行には、肌の色違いを並べない | 32 | 無い |
| B: どの行にも肌の色違いを並べない | 4（`はた`、`かお` など） | 肌の色違いのすべて |
| C: 行の長さに上限を設け、超えた分の候補を末尾から外す（どの絵文字も、少なくとも 1 つの行に残す） | 0 | 無い |

A と B では長い行が残る。C を試作し（上限 4,000 文字）、DDSKK ですべての見出し語を引いた結果は次のとおりである。

- 上限を超えた見出し語: 54 個。外れた候補: 5,472 個（全体の 34,363 個の約 16%）
- 最長の行: 3,999 文字。DDSKK で引けない見出し語: 0 個（17,310 個中）
- どの絵文字（肌の色違いを含む）も、少なくとも 1 つの見出し語に残る
- 例: `じょせい` 785 → 86 候補、`かっぷる` 312 → 47、`はーと` 251 → 71、`かお` 390 → 138、`はた` 269 → 99
- 辞書の大きさ: EUC-JP 版 4.72 MB → 3.63 MB、UTF-8 版 3.64 MB → 2.80 MB
- 実際のキー入力でも、`Q h a - t o SPC`、`Q ! h a - t o SPC`、`/ a b a c u s SPC` が絵文字に変換される

C を採る。

## 実装すること

### 行の長さの上限

- 上限を、EUC-JP 版の 1 行の文字数で 4,000 文字とする（`MAX_LINE_LENGTH`）。DDSKK が見落とす 5,000 文字に余裕を持たせた値である
- 行の長さは、`renderEucJp` が書く行（見出し語、空白、`/`、候補の Lisp の式、`;`、注釈、`/`）の文字数（コードポイントの数）で、改行を含めない。この計算を `src/lib/skk.ts` の `eucLineLength(headword, candidates)` にまとめ、`renderEucJp` の出力と一致させる
- `!` の付いた見出し語の行は 1 文字長いので、上限と比べるのは `!` を付けた行の長さとする

### 候補の外し方

`src/lib/skk.ts` に純粋な関数 `limitLineLength(dict, max)` を足す。

1. すべての行について、各絵文字（肌の色違いを含む。候補の `emoji` で区別する）が現れる行の数を数える
2. 見出し語を UTF-8 のバイト順に 1 つずつ処理する。行が上限を超えていれば、候補を末尾から順に見て、その絵文字がほかの行にも残っていれば外す（現れる行の数を 1 減らす）。ほかの行に残っていなければ、外さずに 1 つ前の候補に進む。上限に収まった時点で止める
3. 外せる候補が無くなっても上限を超えている行があれば、その見出し語を示して例外を投げる（`build` は失敗する）
4. 受け取った `Dictionary` は書きかえず、新しい `Dictionary` を返す。`emojiCount` と `warnings` は変えない

候補の並びの末尾には、肌の色違い、次に `ime_readings` だけで当たった絵文字が来る（「候補の並び順」）。そのため、重要度の低い候補から外れる。

### 生成の手順

- `src/build.ts` は、`collect` の結果を `limitLineLength` に通し、その結果を `withBangHeadwords` に通してから、2 つの版を出力する。UTF-8 版も同じ候補にする
- `build` は、上限で候補を外した見出し語の数と、外した候補の数を表示する

### 文書

- `docs/specifications.md` に「行の長さ」の節を足し、上限と外し方を書く。「既知の問題」の DDSKK の節を、この ADR で直したことに書きかえ、[ADR 0002](0002-bang-prefixed-headwords.md) の実装で書いた引けない見出し語の数（1,242、2,483）を、数値変換による見かけの失敗を除いた数（1,159、2,317）に直す。ADR の一覧に足す
- `README.md` の「DDSKK の既知の問題」を消し、広い意味の読み（`じょせい` など）では候補の一部を外していることを書く

## 実装しないこと

- DDSKK による検査を CI に入れること。SKK-JISYO.kaomoji のような Docker の環境と検査の仕組みが要るので、別の ADR で決める
- 候補の順位の付け方（「候補の並び順」）の変更
- 見出し語ごとに上限や外す候補を手で決める設定
- UTF-8 版だけ別の上限にすること
- DDSKK の数値変換と、数字を含む見出し語の扱い。実際のキー入力では引ける
- libskk など、DDSKK 以外の実装の検索の調査

## テスト設計

実装の前に次のテストを書いて失敗させてから実装する。

### `tests/lib.test.ts`（`deno task test`、`npm test`）

1. `eucLineLength`: 小さな辞書を `renderEucJp` で出力し、各行の文字数が `eucLineLength` と一致する（肌の色違いと、`/` を `／` にした注釈を含める）
2. `limitLineLength`: 上限を超える行から、候補が末尾から外れ、上限以下になる。残った候補の順は変わらない
3. `limitLineLength`: 末尾の候補の絵文字がほかの行に無いときは、それを残して 1 つ前の候補を外す
4. `limitLineLength`: 2 つの長い行に同じ絵文字があるとき、UTF-8 のバイト順で先に処理する行から外れ、後の行には残る
5. `limitLineLength`: どの候補も外せずに上限を超える行があると、その見出し語を含むメッセージで例外を投げる
6. `limitLineLength`: 上限以下の行は変えない。受け取った `Dictionary` を書きかえない。`emojiCount` と `warnings` を変えない
7. `limitLineLength` の上限は、`!` を付けた行の長さと比べる（`!` を付けると上限を 1 文字超える行の候補が外れる）

### `tests/data.test.ts`

8. `data/` から作った辞書（`collect`、`limitLineLength`、`withBangHeadwords`）で、すべての行の `eucLineLength` が 4,000 以下になる
9. 同じ辞書に、`collect` の結果に現れるすべての絵文字（肌の色違いを含む）が、少なくとも 1 つの行に残る

### 実装の後に実際に動かして確かめること

1. Deno と Node.js で生成した辞書がバイト単位で一致する（CI の `node` ジョブ）
2. DDSKK（SKK-JISYO.kaomoji の `Dockerfile` の環境）で、本物の EUC-JP 版のすべての見出し語を `skk-search-jisyo-file` と `limit` 10000 で引き、引けない見出し語が 0 個になる（数値変換は切る）
3. 同じ環境で、SKK-JISYO.L と併せて、`Q h a - t o SPC`、`Q ! h a - t o SPC`、`/ a b a c u s SPC`、`Q r a n d o s e r u SPC` が絵文字を候補に出す
4. 手元の AquaSKK のエンジン（[ADR 0002](0002-bang-prefixed-headwords.md) と同じ方法）で、本物の UTF-8 版の `!はーと`、`!ねこ` が絵文字に変換される

## トレードオフ

- 広い意味の読み（54 個と、その `!` の付いた見出し語）では、候補の一部（5,472 個）が出なくなる。外れるのは主に肌の色違いと、Mozc の読みだけで当たった絵文字である。外れた絵文字も、それぞれの名前の読みなど、ほかの見出し語では引ける。
  785 個の候補を順に見る利用者はまずいないので、実際の不便は小さいと判断した
- 外す候補は、見出し語を処理する順（UTF-8 のバイト順）に左右される。順は決まっているので、同じデータからは同じ辞書ができる
- 上限は、DDSKK の二分探索の実装と `limit` の値（10000）に依存する。DDSKK がこれを変えれば、上限を見直す必要がある
- UTF-8 版も EUC-JP 版と同じ候補にする。UTF-8 版の行は短く、AquaSKK では長い行でも引けるが、2 つの版で候補が違うと、利用者と検査が版の違いを意識する必要がある
- DDSKK による検査を CI に入れないので、行の長さはこの ADR のテスト（`eucLineLength` による上限の確認）で守る。DDSKK の動きそのものは、実装の後とリリースの前に手で確かめる
